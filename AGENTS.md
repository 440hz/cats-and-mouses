# AGENTS.md — инструкции для AI-агента

Рабочая инструкция для AI-агентов (OpenCode и др.), работающих над проектом **CATS AND MOUSES**. Полное описание игры и дизайна — в [GAME.md](GAME.md).

## О проекте

2D-игра в стиле **Pac-Man** с инверсией ролей: игрок управляет мышью, три кота охотятся за ней. Цель — собрать все точки в лабиринте, не попавшись котам.

## Технический стек

- **Язык**: Kotlin 1.9.24
- **Движок**: LibGDX 1.12.1
- **Платформы**: Android (AGP 8.7.0, compileSdk/targetSdk 35, minSdk 24) + Desktop (LWJGL3)
- **Сборка**: Gradle 8.9, Kotlin DSL
- **JDK**: OpenJDK 21

## Команды

| Действие | Команда |
|----------|---------|
| Полная сборка | `.\gradlew build` |
| Запуск Desktop | `.\gradlew lwjgl3:run` |
| Сборка Android | `.\gradlew android:installDebug` |
| Сборка при битых кэшах | `.\gradlew build --no-daemon` |

Тестов в проекте нет (`src/test` отсутствует) — проверкой результата служит `.\gradlew build` (`BUILD SUCCESSFUL`) и, при возможности, запуск Desktop-версии.

## Структура

```
core/        Основная игровая логика (MainGame.kt, GameScreen.kt, MazeLoader.kt, entities/)
android/     Android-модуль (AndroidLauncher.kt)
lwjgl3/      Desktop-модуль (Lwjgl3Launcher.kt)
assets/      Ресурсы (maps/ — карты лабиринта, themes/ — темы локаций, sprites/ — глобальные спрайты персонажей, asset-manifest.json — соответствие asset_id → файлы)
GAME.md      Полное описание проекта и дизайна
```

## Правила изменений (обязательно)

1. **Перед началом работы читай `GAME.md`** — в нём описание проекта, учёт выполненных работ и планы.
2. **Перед началом работы читай подходящие навыки** через инструмент `skill` (список — в системном промпте). Для коммитов и пуша — навык `git-workflow`.
3. **После завершения задачи обновляй `GAME.md`** — разделы «Текущий статус» и «Следующие шаги» (переносить выполненное в статус, актуализировать планы).
4. **Не понижай версии** AGP, compileSdk, Kotlin, LibGDX без явной просьбы — текущая связка (AGP 8.7.0 + compileSdk 35 + Kotlin 1.9.24 + JDK 21) стабильна.
5. **Не трогай `local.properties`** и `opencode.json` без явной просьбы.
6. **Каждое изменение проверяй** через `.\gradlew build` перед тем, как считать задачу выполненной.
7. **Никаких новых библиотек** без необходимости — проект не должен бесконтрольно расти.
8. **Коммиты и пуши** — только по явной просьбе, по процедуре из навыка `git-workflow`.

## Правила пуша в GitHub

- GitHub (remote "github") используется ТОЛЬКО как публичное зеркало.
- Пушить в GitHub только по явной просьбе пользователя.
- Всегда указывай ветку явно:
    git push github master
- ЗАПРЕЩЕНО использовать:
    git push github           (без ветки)
    git push --all github     (зальёт все ветки)
    git push --mirror github  (зальёт всё + теги)
- Gitea (remote "origin") — основное рабочее хранилище.
  Туда пушить часто, после каждого значимого коммита:
    git push origin master

## Правила работы со SpriteCook

Перед ЛЮБОЙ генерацией изображения через SpriteCook (`generate_game_art`, `generate_character`, `animate_game_art`, `generate_tileset`, `create_ui_kit` и другие) — **ОБЯЗАТЕЛЬНАЯ процедура подтверждения**:

### Шаг 1: Проверка баланса
Вызови `get_credit_balance` и покажи пользователю текущий баланс.

### Шаг 2: Список моделей
Вызови `list_generation_models` и покажи пользователю таблицу:
- Название модели
- Стоимость в кредитах
- Краткое назначение (для чего подходит)

### Шаг 3: Рекомендация
Предложи конкретную модель с обоснованием (например: «рекомендую `gemini-3-pro-image` для иконки, потому что качество композиции критично»).

### Шаг 4: Ожидание подтверждения
ЗАДАЙ ВОПРОС пользователю: «Какую модель использовать? Подтвердите выбор или укажите другую».

**СТОП. Не запускай генерацию. Дождись ответа пользователя.**

Исключение: если пользователь ответил **«по умолчанию»** — используй модель по умолчанию (дефолтную из `list_generation_models`) без дополнительных уточнений.

### Шаг 5: После подтверждения
Только после ЯВНОГО СОГЛАСИЯ пользователя — запускай генерацию с выбранной моделью.

### Шаг 6: Отчёт после генерации
Сообщи: сколько кредитов списано, сколько осталось, путь к сохранённому файлу, размер файла.

### Шаг 7: Скачай и сохрани RAW (обязательно)
После генерации ВСЕГДА скачивай **RAW-версию** (`raw_url` из ответа генерации или `get_asset_metadata`) и сохраняй её рядом с основным спрайтом:
- глобальные спрайты персонажей (мышь, коты, сыр) → `assets/sprites/raw/<имя>.png`
- стены/фон темы → `assets/themes/<тема>/raw/<имя>.png`
- иконка/прочие → свои папки (например `assets/icon/raw.png`)

Записывай соответствие `asset_id` → пути (игровой спрайт + raw) в **`assets/asset-manifest.json`** (ключ — `asset_id`, стабилен на сайте) и рядом в **`assets/asset-manifest.md`** (человекочитаемая таблица для визуального контроля, обновлять вместе с JSON), а также в `GAME.md` (раздел «Текущий статус»). RAW — полноразмерный мастер (1024×1024 / 2K / 4K — какое есть): из него в будущем можно перегенерировать/масштабировать игровые спрайты без потери качества и без повторной платной генерации.

### Шаг 8: RAW — только PNG
- При генерации запрашивай ТОЛЬКО **RAW-версию** (`raw_url`), в том разрешении, которое даёт сайт (1024×1024 / 2K / 4K — какое есть). **Pixel-варианты (`pixel_url`) как источник для игры НЕ используй** — игровой размер делается локально из raw.
- Формат проверяй по **магическим байтам файла**, НЕ по Content-Type (SpriteCook может отдавать JPEG-байты с заголовком `image/png`).
- Если полученный raw — НЕ PNG (например JPEG): конвертируй его **на месте в PNG** (для JPEG — ключевание белого фона в прозрачность с мягкой кромкой) и **выведи сообщение пользователю**, например: «Файл X был JPEG → конвертирован в PNG». Разрешения спрашивать НЕ нужно.

### Конвенции по спрайтам
- **Все спрайты** = прозрачный PNG, обрезанный по краю видимой картинки.
- В raw-файлах может быть слабый полупрозрачный ореол/шум (alpha 1–9) — при обрезке резать по порогу **alpha > 10**, а не по нулю.
- Для детализированных raw (не пиксель-арт) ресайз делать ЛАНЦОШЕМ (LANCZOS), не Nearest.
- **Квадратный канвас** и нестандартный экранный размер — только для спрайтов, названных явно.
- **Сыр (`cheese.png`, asset_id `f2cc9aab`) — всегда уменьшен на 40%**: файл-холст **64×64**, контент при (пере)генерации масштабируется до высоты **38px** (60% от 64, ширина ≈34px, пропорции сохранены) и центрируется. На экране при `Pellet.SPRITE_SIZE = 48` сыр выглядит ≈26×29px (на 40% меньше остальных ролей) — осознанное решение, код/SPRITE_SIZE НЕ менять. Общий приём: уменьшение спрайта делается через контент внутри холста, а не через код или распухание канваса.
- **Превью `view/` (только для глаз разработчика)**: после генерации/перегенерации спрайтов рядом с каталогом `raw/` создавай `view/` — те же игровые спрайты, но с прозрачным фоном-шахматкой (чёрные/белые пиксели; 1 клетка ≈ 1 пиксель оригинала, масштаб ~до 512px), чтобы визуально видеть целиком картинку: границы холста и как контент в нём лежит. Генерируется скриптом **`tools/make_view.py`** (Pillow, dev-only).
- **`raw/` и `view/` хранятся в git, но исключены из игровой сборки**: игра в рантайме читает только `sprites/`, `themes/<тема>/`, `ui/` и `maps/`. Из **APK** каталоги вычищаются после merge-задачи (`android/build.gradle.kts`: AGP не фильтрует `sourceSet.assets` через `.exclude()`, поэтому вычистка в `doLast`); из **jar/dist** — исключением в jar-задаче (`lwjgl3/build.gradle.kts`, игровые ассеты остаются в jar). Код не должен обращаться к файлам `raw/`/`view/`.

### Жёсткие ограничения
- НЕ запускай генерацию без явного подтверждения модели пользователем.
- НЕ выбирай модель «по умолчанию» самостоятельно, даже если кажется очевидным.
- НЕ интерпретируй просьбу «сгенерируй спрайт» как разрешение на автоматический выбор модели.
- Исключение: если пользователь в запросе САМ явно указал модель (например, «сгенерируй через gemini-3-pro-image») — тогда не спрашивай, используй указанную.

Это правило действует ВСЕГДА, без отдельных напоминаний от пользователя.

## Конвенции игровой логики

- **Движение строго по сетке** — никакого свободного перемещения. Поворот только в центре клетки.
- **Коллизии считай по клеткам**, а не по пиксельным радиусам.
- **Все ресурсы освобождай в `dispose()`** — SpriteBatch, Texture, ShapeRenderer, BitmapFont.
- **Стиль**: Kotlin, комментарии на русском, без лишних абстракций.
- Изменения карты — в `assets/maps/` (28 колонок × 16 строк, символы `#` — стена, ` ` — проход, `1`–`9` — ручная расстановка сыра, `+` — стартовая клетка мыши).
- Параметры игрового мира меняются через константы в `core` (размер клетки 40, скорость мыши 150, котов 120 и т.д.).

## Известные проблемы

1. **Предупреждение Kotlin Gradle plugin** («плагин загружен несколько раз в разных субпроектах») — безобидно, сборку не ломает. Стандартный фикс (`apply false`) несовместим с AGP 8.7 + Kotlin 1.9.24. **Не исправлять.**
2. **Кэш Gradle иногда повреждается** — при ошибке `Could not read workspace metadata` удалить `%USERPROFILE%\.gradle\caches\8.9\transforms` и пересобрать с `--no-daemon`.

## Типичные задачи и как их делать

- **Добавить/изменить поведение кота** → `core/src/main/kotlin/com/catsandmouses/entities/Cat.kt` (BFS-преследование, патруль, случайное блуждание).
- **Добавить/изменить тему локации** → создать папку `assets/themes/<имя>/` со спрайтами (`wall_0.png` — основной, `wall_1..N` — допы, `background.png` — фон) и `theme.json` (поля: `name`, `wallFiles`, `extrasCountMin/Max`, `background`); зарегистрировать тему в `assets/themes/themes.json` и переключить поле `active`. Читает тему `ThemeLoader.kt`, рисует `GameScreen.kt` (в `extrasCountMin..Max` случайных стенных клеток вместо `wall_0` рисуется случайный доп).
- **Добавить управление мышью** → `core/.../entities/Mouse.kt` + разбор ввода в `GameScreen.kt` (Desktop: WASD/стрелки).
- **Заменить заглушки на спрайты** → пакет `core/.../graphics` (пока не создан), загрузка через `Texture`, рисование вместо ShapeRenderer.
- **Тач-управление Android (свайпы)** → `GameScreen.kt`, обработка `touchDown/touchDragged` в InputAdapter.
